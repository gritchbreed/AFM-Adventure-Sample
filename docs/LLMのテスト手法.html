『血の池の夜』のLLMのテスト手法

端末内の小さなLLM（AFM）を使うゲームを、どう確かめているか（2026-10-09 時点、macOS 版）

生成された文そのものは照合しない。LLM の出力は、同じ入力でもプロンプトの小さな違いやモデルの版で変わります。 そこで、確かめる場所を「決定的な境界」に置きます。 入力の解釈は「どの選択肢を選んだか」、ゲームの進行は「台本のどの行（ID）が出たか」で照合します。 生成の質と安全は、規則で数えるか、人が読んで分類します。LLM に採点はさせません。

層1LLM なしで確かめる

  • 台本の検査（yukemuri validate）：条件・効果・話者が、台本にある定型文・人物・意図・場所を指しているか。定型文の ID の重なり
  • 到達可能性の検査：ゲームの状態を全部たどり、一度も出ない台詞を報告する。入力の解釈は「どの選択肢も選びうる」と仮定するので、LLM がなくても台本の道筋は保証できる。このデモの台本は 15 状態
  • ユニットテスト（Swift Testing。swift test）：エンジンの選び方、条件の書き方の読み取り、解釈の補正の規則、話し相手の決め方、プロンプトの組み立て、出力の検査と作り直し、記憶の選び方、入力の検査、つらさの打ち明けの扱い、話題の引きずりの取り除きなど 70件。LLM の部分は、決まった答えを返す偽物（表で引く解釈、決まった順に返す会話・取り出し）に差し替える
  • 規則だけで動かす（yukemuri trace 意図:メニュー 移動:控え室）：入力を台本での書き方で渡し、出る定型文と次の候補を見る

層2解釈の評価

  • 評価データ（Yukemuri/Evaluation/interpret*.json）は、場面ごとに「そこまでの入力の並び（エンジンだけで状態を作る）」と「発言と期待する解釈の組」を持つ
  • 実機のモデルで流し（yukemuri eval-interpret）、正解率・外れた組・時間を出す。--repeat N で揺れを見る
  • 準備の入力の並びが今の台本と合わなくなると、その場面は飛ばされる（SKIP）。飛ばされたままにしない（元の作品で、移動の経路を変えたら23組が黙って飛ばされていた）
  • 2026-10-09 の基準：話題と移動 39/39、プロンプトインジェクション 10/10。直らない外れは「既知の外れ」として基準に残し、増えたかどうかを見る

層3流し直しと通しプレイ

  • 流し直し（yukemuri replay）：アプリの試作プレイの記録（playlogs/*.jsonl）をそのまま流せる。要所の入力に「期待する解釈」「出るはずの行」「出てはいけない行」「返事が出ないこと」を書き足すと、照らし合わせになる。生成された返事の文は見ない。このデモの基準は 10/10
  • 通しプレイ（yukemuri play 発言 発言 …）：最初から発言を順に送り、出た行と生成の返事、覚えた記憶を読む。解釈のエラーと返事の時間も出る
  • 長い試しプレイ：入力の候補（質問・話題・雑談・移動）から回ごとに違う100個を選んで play に流し、返事の出どころ（生成・作り直し・定型文に戻した）とガードレールの回数を数え、返事を読んで癖（話題の引きずり・食い違い・取り違え）を拾う。2026-10-09 は、これを5回まわして人物の情報を整え（ガードレール 11→3〜5回/100ターン）、攻撃を想定した約130ターンでセキュリティを点検した

層4生成の質と安全

  • 悪意のある入力（yukemuri eval-guardrail Yukemuri/Evaluation/redteam.json）：7分類22件。返事は自動で採点せず、読んで分類する。2026-10-09 は、物語の外に出た返事は0。定型文に戻した2件は、ゲームでは入力の検査で止まる性的な入力（評価では、あえて AFM に渡している）。解釈がガードレールに止められたのが3件（雑談に回り、ゲームは止まらない）。差別的な発言をはっきりたしなめた返事は少なく、「飲んで運転して帰る」に逆の意味の返事（「運転代行だけは頼らないでよ」）が出たこともあり、課題として残る
  • 記憶の取り出し（yukemuri eval-memory）：15/16（外れは「葵は福岡出身だよね」から、主人公の出身として取り出した1件）。雑談への反映（--talk）は 6/6 と 5/6 で揺れた
  • 元の作品での測定：ガードレールの拒否の率は、ほぼ同じプロンプトでも 3〜9/88 と揺れた。比べるときは回数を重ねる
  • 安全に関わる返事は規則で受ける：つらさの打ち明けに、生成が止められて拒否の台詞（「それはあたしの口からは言えないわね」）が出た。規則で見つけて相談窓口を案内し、拒否の台詞は出さないようにした（SessionTests で確かめる）

学びやってみてわかったこと

  • LLM に採点させない（元の作品）：同じモデルに自分の返事の良し悪しを判定させたら、「全部弾く」か「全部通す」に振れるだけだった
  • 候補の並びに敏感（元の作品）：選択肢を1つ足しただけで、別の場面の解釈が変わった。含む語で候補から外れる意図でも起きた。選択肢を足したら必ず回帰を流す
  • 評価の言い方は発言例と変える（元の作品）：発言例とほぼ同じ文は規則で優先されるので、評価に発言例をそのまま入れると数字が甘くなる（発言例と同じ言い方では 18/18、発言例にない言い方では 12/15）
  • 原因の切り分けは写しで（元の作品）：変更を1つずつ外した写しを作って流し、どれで崩れるかを見る
  • まねられる（このデモ）：規則にかぎかっこで書いた言い回しや、台詞の例は、関係のない返事にもそのまま出る。やめさせたい言い回しを規則に書くと、かえって増えた
  • 言葉の取り違え（このデモ）：「ママ」は母親の意味にも取られ、葵の家族を聞いたら店のママの生い立ちで答えた。人物の情報では、紛れる言葉を書き分ける
  • 記録が手がかり（元の作品）：試作プレイの記録に、候補・選んだもの・自由会話のプロンプト・生成元（生成／作り直し／定型文に戻した）を残す。原因の多くは、プロンプトを読むとわかる。アプリのデバッグの画面（メニューの「開発」）でも同じものが見られる

運用回してみる順番

  • 作業の始めと終わりに tools/regress.sh（検査・ユニットテスト・解釈の評価・流し直し。流し直しまでなら --quick、検査とユニットテストだけなら --validate）
  • 台本を直したら：検査 → 流し直し・解釈の評価 → 通しプレイで該当の場面
  • 試作プレイで見つかった入力は、直した後に流し直しか解釈の評価の例として足す
  • 事実を聞かれやすい問いや、物語の筋に関わる話は、生成に任せず台本（定型文）か「知っていること」に移す。テストで守る範囲を広げるより、生成に任せる範囲を狭めるほうが確実

道具：Swift パッケージ Yukemuri のコマンド yukemuri（validate・trace・play・replay・eval-interpret・eval-guardrail・eval-memory）、tools/regress.sh、Swift Testing。評価データは Yukemuri/Evaluation/、結果は Yukemuri/results/（入力文を含むのでリポジトリに入れない）。数値は 2026-10-09 時点、M4 の MacBook Air・macOS 27.0.1 での測定。AFM の使い方は「AFMの使い方.html」を参照。
